# Codebase map

> One screen. The only living document of the repo: it is updated when the shape of the code changes, not at every PR. Updated on 2026-10-03.

## What it is

The harness repo: the Claude Code skills that build the agent production chain, the templates that land in the project repos, the spec that describes it. There is no application: the product is markdown files, bash scripts, workflows and a JSON schema.

## Data flow

Since ADR-0003 the prose of this repo, `docs/**` and the `SKILL.md`, lands on main with a commit, and the human's yes in the conversation is the approval: `pre-commit` and `pre-push` read `docs_mode` from the policy block and let through on main a commit made only of the paths of `human_gate_paths` and `docs_extra_paths`. Scripts, hooks, workflows and tests land with a PR from the four gates, merged by hand, with no judgement by default. In the project repos it arrives by rerunning the stage of `/harness-init` that owns that file, which rewrites what is its own and keeps the local changes where they do not conflict, the policy block key by key because a flat rewrite would carry away the `sensitive_paths` somebody widened on purpose, and it is the only way: a skill working in there that sees the harness behind writes a dated line in that repo's `.harness/docs/inbox.md` and carries on, without touching scripts, hooks, workflows or `AGENTS.md` (ADR-0003, decision 4). For the same decision the hook that refuses the PR of a head with no verdict stays in the template and not in the `.claude/settings.json` of this repo: the projects have the gate, this repo runs `/judge` on request. Claude Code reads the skills from `~/.claude/skills/`, where every skill of `skills/` is a symlink to this checkout: the working tree is what runs, in every project. The spec changes with a new version at the top and a line in "What changes".

## How to run it and test it

pnpm test · pnpm typecheck · pnpm format:check · pnpm build

Every script of the templates has its tests, which run it as a process with a message or a disposable git repo as the fixture. A disposable repo has a base commit, a work commit, the real `.harness/AGENTS.md` copied in and the base files a case asks for, such as a slice, so the policy block a script reads is the repo's own; `tests/agents.ts` rewrites it key by key when a case wants a different policy. Where a script needs a remote, the fixture is a clone of a disposable bare origin, so the default branch comes from `origin/HEAD` as in a real clone; where it runs a hook, `core.hooksPath` points at the hooks of the template. `tests/fixtures/bin` holds the stubs: `gh` records the calls, keeps the bodies of the comments and answers the reads (head, labels, comments) from the `STUB_*` variables, `STUB_FAIL` makes a chosen call fail to prove that a network error does not leave the PR mute, `curl` records the notifications, and a `pnpm` that passes or that runs the repo's Prettier stands in for the real one. A tool that must be missing, `gh` on the laptop and in CI alike, is missing because `PATH` is made only of symlinks to the tools the script uses. A rule with branches in order gets one fixture per branch that strips the facts of the branches before it, so the case proves the order and not only the rule. A test whose subject is a gate is written so that it passes the gate: the dash is spelled as an escape, and the three words of the command the verdict hook looks for never appear as a single string, or the hook would block the writing of the file.

`architecture.test.ts` is where a rule of the repo that a check can enforce lives, and a session opens it to find one: the lines of the Do not, the copies in `.github/` derived from the template directories instead of from a list written in the test, `.harness/docs/README.md` equal to its template with a section per folder and no README of a folder left, the policy block of `.harness/AGENTS.md` and of its template read with `jq`, the root `AGENTS.md` with its `## Harness` section and no block and its raw fence in ascii, the frontmatter of every `SKILL.md`, the skeletons that must say what the sections of the README say, read through `tests/docs.ts`, and the verdict schema with the minimal validator of `tests/schema.ts`, which refuses every keyword it does not know.

`.harness/bin/tier.sh main` and `.harness/bin/test-weakening.sh main` give the same output locally as in CI. The judge is tried by running `/judge` on a real branch: same prompt, same schema, and `.harness/bin/judge.sh check` in place of `--json-schema`. `vitest.config.ts` declares a `testTimeout` of 20 seconds, because almost every test builds a real git repo and with vitest's default, 5000 ms, the suite failed at random locally under load. `typecheck` is `tsc` over the tests plus `.harness/bin/check-shell.sh`. `build` does nothing and says so. There is no `dev`: `/harness-init` is tried by running it in another repo, `/spec` on an intent of Tipoff, `/slice` on an approved spec of Tipoff.

## Dragons

- The symlink in `~/.claude/skills/` points at the working tree: a half finished branch or an uncommitted change is already live in every other repo. Work on short branches and go back to main before using the skill elsewhere.
- The scripts of the templates run on the bash 3.2 of macOS, without brew: no bash 4 constructs. The structural test looks for the known ones (mapfile, associative arrays, `${var,,}`, `|&`); `bash -n` on the bash 5 of CI does not see them.
- The templates go through Prettier both here and in the repo that receives them: a template that is not stable under Prettier is rewritten at the project's first commit. The placeholder lines are list items for this reason. The globs the scripts read live in JSON strings inside the policy block, where Prettier touches nothing; since S39 the backticks in the prose lines serve only the reader, because nobody runs those lines any more. Before that the backtick was the gate: without it Prettier read the `*` as emphasis and rewrote the globs into something `tier.sh` no longer recognised, silently. It happened, and the test that every named path exists is there for that.
- The inputs of `actions/create-github-app-token`, `pnpm/action-setup` and `actions/setup-node` change between majors: the workflows are written by reading the current doc, never from memory.
- The files of `.github/workflows/` are copies of the templates, not symlinks like the scripts and the hooks: GitHub Actions does not follow a symlink inside `.github/workflows/` and the workflow is not registered. A copy drifts silently, and it happened: at the time of PR #9 five workflows out of six were three slices behind while the scripts were today's, and no test saw it because it looked only at the templates. The comparison in `architecture.test.ts` is what keeps the copy honest; a workflow that changes is carried back by rerunning the stage of `/harness-init` the test names, not by editing the copy. The comparison looks from the side of the templates, because under `.github/` there are also files that are born there and copy nothing: the list is the templates themselves and the destination is given by the structure of the directories, so a new template enters the check without anyone adding it. It was needed: `pull_request_template.md` was outside the hand written list and its copy stayed one section behind for the whole of S12. The judge prompt and the schema were copies of the same species until S90, the prompt equal to its template only above `## This repo`; now they are machinery, read from `.harness/bin/judge/`, and the lines of the repo for its judge are `.harness/judge.md`, a tracked file of its own that `judge.sh bundle` puts right after the prompt.
- `automerge.yml` runs only from main (`workflow_run` reads the workflow from the default branch): a change shows up at the PR after the merge, not in the PR that carries it. It held for `judge.yml` too, the cloud judge that left the templates on 15 September (ADR-0004): the judge is `/judge`, in the terminal, and no workflow calls a model.
- The base guard of `close.yml` is half proven. On 2026-09-15 PR #32, merged into `prova/base-non-default`, left the `close` job skipped and ran `stacked`, whose log prints the three resolved contexts: `PR: 32`, `BASE: prova/base-non-default`, `DEFAULT_BRANCH: main`. Under `pull_request` therefore `github.event.repository.default_branch` exists and holds what it must, which was the doubt written in the comment of the template; main did not move and `verdicts.jsonl` stayed at 38 lines. The two branches of the trial are deleted, the trace is PR #32 and its run. The same reading under `workflow_run`, the one of `automerge.yml`, is not proven and will not be while `HARNESS_AUTOMERGE` is off, because that workflow does not reach the point where it makes it: whoever turns it on should watch that first run, and know that an empty field stops every merge instead of letting one through. Since S16 the same question is asked by the third one too, `policy.sh`, which has no event to read and asks `gh` for the base and the default branch: that one is covered by the tests, and the empty value stops it like the other two.
- The local verdict lives under the common git dir, in `$(git rev-parse --git-common-dir)/harness/<sha>.<role>.json`, which in the main checkout is `.git/harness/`, and not in the tree. The common git dir and not the checkout's: inside a worktree the git dir is `.git/worktrees/<name>`, and `git worktree remove` at the hand-back of `/next` would carry the verdicts away with it (S25); the store is one per clone, and a verdict made in a worktree is read from the main checkout and the other way round. Outside the tree because a verdict file in `docs/` or at the root would end up in the diff the judge is judging. It is not tracked, it is not cloned and it does not survive a fresh checkout: whoever picks up a branch from another computer runs `/judge` again, and that is right, a verdict holds for a commit and for whoever saw it. It holds for one base too, the one `judge.sh check` prints inside it as `base_sha`: the same head against two bases are two diffs, and the hook compares the merge base before opening the PR. Since ADR-0003 the judge runs once per PR: the verdict stays the judged commit's, `judge.sh answer` writes next to it the commit that closes each finding, and the hook opens the PR on a commit that answers, never on one that answers nothing. The answers are stripped by `check` if the judge writes them; at tier 2 a fix that answers one role carries the other along, because the two judged the same head. `policy.sh` merges only with CI green on the head of the PR, and the log gives the merge to the policy by reading the last line of its comment, because the login is a person's.
- `ensure-verdict.sh` reads as a command every line that starts with `gh pr create`, even inside a heredoc: it does not parse the shell, and at the start of a line there is nothing that says prose. A file that shows the PR in a code block, such as a SKILL.md, is not written with a heredoc in Bash, because the hook stops the call and the file is never born. It is written with the writing tool, which the hook does not see. Since S13 the hook is not installed here and the bite is felt only in the project repos, where the template installs it: whoever writes a template that shows that command tries it there, not here.
- A finding with `by: human` exists only in the stored verdict of the clone where `/judge` ran: `judge.sh check` strips it from what the judge hands over, and `policy.sh` reads only a stored verdict. In another clone `judge.sh finding` says there is no verdict, and that is right, as it is for `answer`. An open human `high` or `medium` stops the merge whatever the verdict says, because the judge had already spoken when it arrived, and in `policy.sh` it is the only branch that looks at who found the finding instead of at the severity alone.
- `docs/spec.md` is not a `SPEC-<slug>.md`: it has no `status`, it does not become `superseded`. The feature specs of this repo, when there are any, live in `.harness/docs/specs/`.
- `.harness/docs/backlog/**` is among the human merge paths, and the gate holds for the PR that goes through it too: a slice PR that touches the file of its own slice takes `human-gate` and the policy does not merge it, not even at tier 1 with zero findings. It happened on Tipoff on 16 September, four esc-key slices closed by hand with `HARNESS_AUTOMERGE` on, for the commit that 4.4 and `/next` asked for at step 2 and that moved the slice to `in-progress`. Since S19 that commit is gone: the claim is the branch on the remote, `in-progress` leaves the states, and the case in `tests/tier.test.ts` holds the gate still, which is wanted, because no PR should change the criteria of a slice without a human. Here it had not shown up because every PR is merged by Lionel anyway: a defect of the chain shows up in the repo that uses it, not in the one that builds it.
